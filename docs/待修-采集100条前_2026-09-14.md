## P0-1 · 「更新」是整条替换，会静默清空投递历史 ⚠️ 本地不可逆 + 两端永久不一致

**位置**：`extension/content.js:918-921`

```js
const i = jds.findIndex((x) => x.key === rec.key);
const isNew = i < 0;
if (isNew) jds.push(rec);
else jds[i] = rec;          // ← 整条覆盖
```

**问题**：`rec` 是 `extract()` 从当前页面现抓的，只包含页面上有的字段。
**`status` / `statusHistory` / `failReason` / 批量补过的 `salary` 都不在里面。**

所以一个已经标成「已投」甚至「进面」的岗位，只要再按一次 `Alt+S`，
投递历史直接归零，而 toast 还显示「已更新 ·」，看不出发生了什么。

**为什么是 P0**：`extension/lib/pipeline.js` 文件头自己写着 ——
「时间戳一旦没记就永远补不回来，等投了 30 个岗再想做漏斗，
只能看到一堆已挂，不知道各自挂在第几天」。
100 条规模下重复点到已存岗位是必然事件。

### 后果比「本地丢了」更麻烦一点（2026-09-14 追查同步链路后补）

云端那份**其实还活着**，但插件永远拿不回来。三个事实凑出来的：

1. `syncSupabase.js:298` 推送时，`job.status` / `job.intent` / `job.failReason`
   都是 `undefined` → `JSON.stringify` **直接把这几个键丢掉** →
   PostgREST 的 `merge-duplicates` 只 SET 载荷里出现过的列，
   **没出现的列保持原值**。所以云端的 status 没被覆盖。
2. `syncSupabase.js:328` 那段「先删云端历史再整批插」外面裹着
   `if (job.statusHistory && job.statusHistory.length)` ——
   本地历史被清空后长度为 0，**整段被跳过**，云端历史也没被删。
3. 而 `syncAll` 只拉两样东西：**云端删除墓碑**和**简历**
   （`pullDeletions` / `pullResume`）。**它从不把 JD 状态拉回本地。**

所以真实的坏法是：**工作台显示「已投 · 进面 · 3 条轨迹」，插件弹窗显示空白，
而且下一次同步不会修复这个分歧，只会让它一直存在。**
数据没消失，但你会看到两个界面各说各话，而没有任何提示告诉你哪个是对的。

> 这和 web 端 P1.7 修的是**同一个 bug 的两侧**：拿一份不完整的旧数据盲写覆盖。
> web 那边的解法是乐观并发（读时记版本、写时当条件），这边不需要那么重 ——
> 这边的两个写入方（页面采集 / 弹窗操作）**写的字段本来就不重叠**，
> 合并就够了。

**建议改法**：更新走合并，页面抓不到的字段一律保留旧值。

**建议改法（2026-09-14 对齐过字段清单后的版本）**：

```js
else {
  const old = jds[i];
  /* 手填过薪资的记录，这次页面抓到什么都不许动薪资那一组 ——
     它们四个必须同进同退，只保 salary 会造出
     「salary 有值、salarySource 是空、salaryParsed 是 null」这种自相矛盾的记录。 */
  const keepSalary = old.salarySource === "手填" || rec.salaryBlocked;
  jds[i] = {
    ...old,
    ...rec,
    // ── 只存在于本地流转、页面永远抓不到的字段，一律保留 ──
    status:        old.status,
    statusHistory: old.statusHistory,
    failReason:    old.failReason,
    intent:        old.intent,        // 🔥/👀/❌，你在弹窗里手点的
    salaryPending: old.salaryPending,
    // ── 薪资四件套：要么全用旧的，要么全用新的 ──
    ...(keepSalary
      ? {
          salary:        old.salary,
          salarySource:  old.salarySource,
          salaryParsed:  old.salaryParsed,
          salaryBlocked: old.salaryBlocked,
        }
      : {}),
    // 采集时间保留首次，另记一个最后更新时间
    ts:            old.ts,
    updatedAt:     new Date().toISOString(),
  };
}
```

> **和上一版建议的三处差别，都是对着代码核出来的：**
>
> 1. **补了 `intent`**。它是你在弹窗里手点的意向（`popup.js:232` 的
>    `setField(r.key, "intent", …)`），`extract()` 不产出它 ——
>    上一版漏了，等于每次重存都把意向清空。
> 2. **删掉了 `note`**。全项目没有这个字段（`popup.js` 里的 `note` 是个 CSS 类名，
>    不是数据字段）。写上去只会让下一个人以为有。
> 3. **薪资从两个字段改成四个一起保**。`popup.js:63-70` 手填薪资时写的是
>    `salary` / `salarySource` / `salaryParsed` / `salaryBlocked` / `salaryPending`
>    **五个**；上一版只保 `salary` 和 `salaryPending`，
>    重存之后会变成「salary 还是手填的那个值，但 salarySource 被覆盖成空、
>    salaryParsed 被覆盖成 null」—— 一条看起来正常、实际内部对不上的记录。
>    而这种记录最麻烦：它不报错，只是以后按薪资排序时它悄悄排不进去。
>
> 已核对过的字段清单（`content.js:798` 那个对象字面量）：
> `extract()` 产出 `jobId / key / url / title / company / tagline / salary /
> salarySource / salaryParsed / salaryBlocked / salaryConflict / body /
> pageText / site / ts`。
> 除此之外出现在记录里的，全部是本地流转字段，都要保。

**验收**：手工造一条 `status: "已投"` + 有 `statusHistory` 的记录，
在同一个岗位页面再按一次 `Alt+S`，两个字段都还在。

## P0-2 · jobId 取空时静默退回 URL 做键

**位置**：`extension/content.js:801`（键的生成）、`content.js:899`（守卫失效）

```js
key: jobId || location.href.split("?")[0],   // 有 jobId 就用它，没有才退回 URL
```

**问题**：`getJobId()` 三级都取不到就返回空串，于是 key 退回 URL ——
而 v1.0 的致命 bug 正是「新版列表页所有岗位共享同一个 URL」，
`content.js:127` 的注释就记着这件事。降级发生时界面**没有任何提示**，
toast 照常显示「已存」。

更麻烦的是 899 行那个防错守卫：

```js
if (panel.switched && panel.wantId && rec.jobId && rec.jobId !== panel.wantId) {
```

`rec.jobId` 为空是 falsy，**整个守卫被短路跳过** —— 恰恰在最该拦的情况下不拦。

**建议改法**（两处都要）：

1. `key` 为 URL 时，toast 走 `warn` 并写明「这条用 URL 做键，可能与同页其他岗位互相覆盖」
2. 899 行的守卫补一个分支：`panel.switched && panel.wantId && !rec.jobId` 时也拒存，
   或至少警告

**验收**：在列表页故意让面板取不到 id（或临时把 `getJobId` 前两级 return 掉），
确认存的时候有明确警告，而不是安静地存进去。

## P0-3 · key 不带站点前缀

**位置**：`extension/content.js:801`

现在 key 就是裸 jobId。只有 BOSS 一个站时没问题，但 ROADMAP **P6 要加猎聘 / 智联**，
两个站的 id 空间没有理由不撞。

**建议改法**：`key: jobId ? "boss:" + jobId : location.href.split("?")[0]`

**为什么现在改**：库里只有 2 条，改完重采即可。采完 100 条再改就要写数据迁移。

**⚠️「成本为零」要打个折（2026-09-14 核过云端约定后补）**

已确认：`syncSupabase.js:298` 推的 `job_key` **就是本地的 `key`，一模一样**，
没有第二套约定 —— 这是好消息，改一处就够。

但正因为是同一个键，**云端已经同步过去的那几条会变成孤儿**：
`career_jds` 里躺着 `12345678`，本地从此叫 `boss:12345678`，
再同步只会**多插一条**，不会更新原来那条。

而且删不掉：本地删除走墓碑（`flushTombstones`），墓碑也是按 key 记的，
你删掉本地的新记录，写的是 `boss:12345678` 的墓碑，
和云端那条老的 `12345678` 对不上。

**所以顺序是**（2026-09-14 实施时又改进了一次）：

**在插件弹窗里删掉那 2 条**（不是在工作台删）→ 重新加载扩展 → 重采。

为什么是弹窗不是工作台：弹窗的删除走 `popup.js` 那条**三件事一起做**的路径 ——
本地删除 + 写删除墓碑 + 下次同步时把云端那条也删掉（`flushTombstones`）。
而此刻墓碑记的还是旧键，和云端那条的 `job_key` 正好对得上，删得干净。
等换了新版再删，墓碑记的是 `boss:12345678`，和云端的 `12345678` 对不上，
那两条就真的只能进 Supabase 后台手动清了。

> 这仍然比采完 100 条再改便宜得多 —— 那时候要清的是 100 条，
> 而且其中一部分已经标过投递状态了。
