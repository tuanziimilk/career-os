# 迁移方案 · 两个仓库合并为一个

> 2026-09-15 · 前提：采集和改动都已停止，两个仓库工作区都干净。
> **核心原则：合并仓库 ≠ 合并运行时。** 扩展仍然零构建，工作台仍然独立 vite build。
> 变的只有「它们在不在同一个 git 历史里」。

---

## 为什么现在做，以及为什么理由不是「看起来乱」

真正的理由在 `career-web/scripts/check-thresholds.mjs:33-35`：

```js
/* 登记表里的 file 是**相对仓库组根目录**写的（career-web 和 jd-insight 是兄弟目录），
   这样一眼能看出某个阈值属于哪一端。 */
const ROOT = resolve(HERE, "..", "..");
```

**代码里已经有「仓库组根目录」这个概念了 —— 只是 git 里没有对应的东西。**

现状的三个后果，都是真实的：

1. `career-web` 的 `npm run build` 会伸手读 `../jd-insight/extension/lib/salary.js`。
   换台电脑、文件夹名不一样，build 直接挂，而且报错会指向一个不存在的路径
2. 两端的共享物（薪资解析 / 技能词典 / 漏斗常量）靠 `check:shared` **事后检测分叉**，
   但 git 里没有任何记录说「web 的这个 commit 是对着扩展的哪个 commit 校验通过的」
3. 09-14 改 key 前缀同时影响 `extension/lib/jdMerge.js` 和云端 `career_jds` 的读取方，
   **没法做成一个原子提交，也没法一起回滚**

合并不是引入耦合，是把**已经存在的耦合**变成 git 能看见、能约束的东西。

---

## 目标结构（阶段一之后）

```
career-os/                      ← 一个 git 仓库，基底是 jd-insight 的 46 条历史
├── extension/                  ← 原样不动，仍然零构建
├── analyzer/                   ← 原样不动
├── scripts/                    ← 原样不动（扩展侧的 eval-*）
├── eval/  data/  reports/  assets/
├── docs/
├── web/                        ← career-web 整个搬进来，14 条历史保留
│   ├── src/  scripts/  supabase/  public/
│   ├── package.json            ← 仍然在这一层 npm install / npm run build
│   └── vite.config.ts
├── ARCHITECTURE.md  CHANGELOG.md  MAINTENANCE.md  README.md  LICENSE
└── .gitignore                  ← 两份合并
```

**`web/` 里保持原样**，不动它的 package.json、不做 npm workspace。
理由：workspace 会改变 `npm install` 的行为和 node_modules 的位置，
而这一步的目标是「除了位置什么都不变」。

## 阶段一 · 只搬位置（约 30 分钟，全程可回滚）

### 0. 先备份（两分钟，别跳过）

```bash
cd "D:/python-tool/简历/大Zo"
cp -r jd-insight jd-insight.bak-20260915
cp -r career-web career-web.bak-20260915
```

两个仓库都已推到 GitHub，理论上远端就是备份。
但 subtree 会改写本地历史的形状，本地留一份最省心。

### 1. 用 subtree 把 career-web 并进来（保留两边历史）

```bash
cd "D:/python-tool/简历/大Zo/jd-insight"
git remote add web-src ../career-web
git fetch web-src
git subtree add --prefix=web web-src main
git remote remove web-src
```

> **分支名先确认**：如果 career-web 的主分支不叫 `main`，
> 用 `git -C ../career-web branch --show-current` 查出来替换。
>
> 这一步之后 `git log --oneline | wc -l` 应该是 **46 + 14 + 1 = 61 左右**
> （多出来的 1 是 subtree 的合并提交）。数字对不上就说明 fetch 的分支不对。

### 2. 修唯一会断的两处

**① `web/scripts/check-shared.mjs`** —— 三处路径。
`root` 是 `resolve(here, "..")`，合并后 = `<repo>/web`，所以去掉 `jd-insight/` 一段即可：

| 行 | 改前 | 改后 |
|---|---|---|
| 32 | `resolve(root, "../jd-insight/extension/lib/salary.js")` | `resolve(root, "../extension/lib/salary.js")` |
| 35 | `resolve(root, "../jd-insight/extension/lib/skills.js")` | `resolve(root, "../extension/lib/skills.js")` |
| 133 | `import("../../jd-insight/extension/lib/pipeline.js")` | `import("../../extension/lib/pipeline.js")` |
| 154 | 错误文案里的 `jd-insight/extension/lib/pipeline.js` | `extension/lib/pipeline.js` |

**② `web/src/data/thresholds.json`** —— 18 项的 `file` 字段要去掉/换前缀：

- 14 项 `jd-insight/...` → 直接去掉前缀，变成 `extension/...` / `analyzer/...`
- 4 项 `career-web/...` → 换成 `web/...`

一条命令搞定（改完用 `git diff` 看一眼）：

```bash
cd "D:/python-tool/简历/大Zo/jd-insight"
python - <<'PY'
import io, json
p = "web/src/data/thresholds.json"
d = json.load(io.open(p, encoding="utf-8"))
for t in d["thresholds"]:
    f = t["file"]
    if f.startswith("jd-insight/"):
        t["file"] = f[len("jd-insight/"):]
    elif f.startswith("career-web/"):
        t["file"] = "web/" + f[len("career-web/"):]
io.open(p, "w", encoding="utf-8", newline="\n").write(
    json.dumps(d, ensure_ascii=False, indent=2) + "\n")
print("ok")
PY
```

> ⚠️ 写回时注意 **缩进和换行符要和原文件一致**，否则 `check:eol` 会红。
> 原文件是 2 空格缩进 + LF 的话上面这段就是对的；先 `git diff` 确认只有
> `"file"` 那些行变了，别整个文件重排。

**③ `check-thresholds.mjs` 的 ROOT 不用改。**
`HERE` = `<repo>/web/scripts`，`resolve(HERE,"..","..")` = `<repo>` —— 正好就是新的仓库根。
只要把第 33 行那句注释从「career-web 和 jd-insight 是兄弟目录」
改成「相对仓库根目录」就行。**这是合并带来的第一个简化。**

### 3. 合并 .gitignore

`web/` 自己那份保留（它管 `dist/`、`.env.local`、`supabase/.temp/` 这些 web 专属的）。
根部那份是扩展侧的隐私规则（`analyzer/config.py`、`data/*`、`reports/`），也保留。
**两份各管各的目录，不需要动。** 只确认一件事：

```bash
git status --porcelain | grep -E "node_modules|dist/|tsbuildinfo" | head
```

有输出说明 subtree 把不该进的东西带进来了 —— 那就 `git rm -r --cached` 掉再提交。

### 4. 验收（三条都必须绿）

```bash
# ① 扩展侧全套评测
cd "D:/python-tool/简历/大Zo/jd-insight"
node scripts/eval-all.mjs

# ② 工作台完整 build（含 6 道闸门）
cd web && npm run build

# ③ 确认历史都在
cd .. && git log --oneline | wc -l          # ≈ 61
git log --oneline -- web | wc -l            # ≈ 14，career-web 的历史还在
```

**②最关键** —— 它会依次跑 `check:shared`（验证跨端路径改对了）、
`check:thresholds`（验证 18 项路径改对了）、`check:eol`、`check:diagrams`、
`check:content`、三套 eval、`tsc -b`、`vite build`。
全绿就说明搬对了。

### 5. 提交并推送

```bash
git add -A
git commit -m "$(cat <<'EOF'
合并仓库：career-web 以 subtree 并入 web/

两端在构建期本来就耦合（check-shared 读 ../jd-insight/、
check-thresholds 的 ROOT 已经假定了「仓库组根目录」），
但 git 看不见这层依赖，也就无法保证两边版本对得上。
合并后这层耦合变成仓库内的相对路径，可原子提交、可一起回滚。

运行时不变：扩展仍零构建，web 仍在 web/ 下独立 vite build。

改动仅三处路径：
- web/scripts/check-shared.mjs 的三条跨仓库引用
- web/src/data/thresholds.json 的 18 项 file 前缀
- check-thresholds.mjs 里那句已经过时的注释

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
EOF
)"
git push
```

### 回滚

阶段一之内任何时候出问题：

```bash
git reset --hard origin/main      # 回到 subtree 之前
```

已经 push 了也不慌 —— 两个 `.bak-20260915` 文件夹还在，
`career-web` 那个独立仓库**一个字节都没被改过**，它还在原地、还能推。

## 阶段二 · 抽 shared/ 层（另一天，别和阶段一混）

**为什么要分开**：阶段一是纯机械操作，出问题一眼能看出是哪一步；
阶段二要改真实的 import 路径，属于逻辑改动。混在一起，
build 红了你分不清是搬错了位置还是拆错了模块。

目标：

```
shared/
├── salary.js          ← 唯一权威，两端都 import 它
└── skills.json        ← 唯一权威
```

做完之后 **`check:shared` 可以退化甚至删掉** ——
它现在的工作是「事后检测两份副本有没有分叉」，
有了 `shared/` 就根本只有一份，没有分叉的可能。

> 但扩展那边有个已知约束：`skills.json` 不能直接 `import` JSON
> （需要 import attributes，Chrome 123+ 才支持，`check-shared.mjs` 文件头
> 详细记了这个坑）。所以扩展侧仍然需要一个**生成步骤**产出 `lib/skills.js`。
> 也就是说 skills 这一路只能从「复制 + 校验」变成「生成」，去不掉生成。
> **salary.js 那一路是可以真正合一的**，先做那个。

顺带做掉的：`analyzer/config.example.py` 的 `GROUPS` 是另一套已经分叉的旧词典
（ROADMAP 排在 P2.7），`shared/` 建起来之后它应该改成读 `shared/skills.json`。

## 阶段三 · GitHub 上改名（两分钟，可选，最后做）

合并后本地仓库仍叫 `jd-insight`，但它现在装的是整个系统。建议改名：

1. GitHub 上把现有的 `career-os` 仓库改名为 `career-os-web-archive`，并设为 archived
   （**不要删** —— 它是 `web/` 那 14 条历史的独立备份）
2. 把 `jd-insight` 改名为 `career-os`
3. 本地 `git remote set-url origin https://github.com/tuanziimilk/career-os.git`

**GitHub 对改名的仓库会保留重定向**，所以简历或作品集里已经写出去的
`github.com/tuanziimilk/jd-insight` 链接不会失效。

> 排在最后是因为它是唯一一个「对外可见」的改动。
> 前两步失败了没人知道，这一步失败了别人点链接会 404。
> 等 build 全绿、推送成功之后再做。
